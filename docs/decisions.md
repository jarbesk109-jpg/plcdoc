# Decisions

Short records of technical decisions: what was decided, why, and what else was considered.

## 001 — Input format: PLCopen XML
- **Decision:** Read PLCopen XML exports, not vendor project files.
- **Why:** An open, documented exchange format supported by CODESYS and many other IDEs. No reverse-engineering of proprietary formats.
- **Alternatives:** Parsing vendor project files directly (closed, version-dependent).

## 002 — Three layers: core library, API, web UI
- **Decision:** `plcdoc` core library (also published to PyPI) → FastAPI backend → React frontend.
- **Why:** The core works from the command line without the web app and can be tested in isolation.

## 003 — Positioning
- **Decision:** PLCdoc does not try to replace commercial tools such as Copia, VersionDog or Siemens VCI.
- **Why:** It aims to be the open, free, no-install option for students, small shops and small integrators.

## 004 — Sample files as ground truth
- **Decision:** `samples/` holds real CODESYS exports. `samples/CHANGES_v1_v2.md` lists every intentional change between v1 and v2 and is the expected output for diff tests.
- **Why:** Tests run against real data with a known answer.
- **M2.1 extension:** `samples/CHANGES_03_04.md` records the second pair, `03_line_large.xml` → `04_types_qualifiers.xml`.

## 005 — XML parsing goes through defusedxml
- **Decision:** The core library parses with `defusedxml.ElementTree`, the only runtime dependency. The elements it returns are plain `xml.etree` elements, so the rest of the parser is unchanged.
- **Why:** The web backend (M5) will parse files uploaded by strangers. `defusedxml` refuses entity expansion (billion laughs), external entities (XXE) and DTD retrieval, which the standard library parser happily follows.
- **Alternatives:** Plain `xml.etree` (unsafe on untrusted input); `lxml` (fast and safe when configured, but a compiled dependency that is not needed for files of this size).

## 006 — Variables carry their scope and section
- **Decision:** Every `Variable` stores `scope` (owning POU or GVL name) and `section` (`local`, `input`, `output`, `inout`, `global`, ...). Section names are derived generically from the `*Vars` tag name; unknown ones are still mapped and reported in `Project.warnings`.
- **Why:** The I/O table, the cross-reference (M3) and the diff (M4) all key a variable by `(scope, name)`. Storing it once at parse time keeps those modules free of tree walking, and the generic mapping means a new CODESYS section does not break parsing.
- **Alternatives:** Derive scope from ownership at query time (every consumer repeats the walk); a hard-coded list of sections (fails silently on anything new).
- **M2.1 amendment:** Decision 010 adds configuration/application ownership and replaces the variable key with `(application, scope, name)` within a configuration.

## 007 — Natural address ordering
- **Decision:** `parse_address` splits `%IX0.7` into `(area, size, path)` and the I/O table sorts by area (I, Q, M), then size (X, B, W, D, L), then the numeric path. `%IX1.0` therefore follows `%IX0.7` and `%IX0.10` follows `%IX0.2`. Unparseable addresses go last in string order.
- **Why:** String order puts `%IX0.10` before `%IX0.2` and `%IX1.0` before `%IX0.7`, which is unreadable in an I/O table.
- **Alternatives:** Document order (depends on how the author declared things); pure string order.

## 008 — CLI prints Markdown tables; JSON output is deterministic
- **Decision:** `plcdoc parse` prints Markdown tables (reused by the M3 Markdown export). `plcdoc parse --json` dumps the `Project` dataclasses with sorted keys, parse-order lists and unescaped UTF-8.
- **Why:** Readable in a terminal without extra dependencies. Deterministic JSON lets tests and the M4 diff compare outputs byte for byte, and M5 can return the same structure from the API.
- **Alternatives:** `rich`/`tabulate` for prettier tables (extra dependencies); YAML output.

## 009 — POU discovery covers three locations
- **Decision:** POUs are read from `types/pous/pou` first and then from every CODESYS `data[@name=".../plcopenxml/pou"]` element; the first POU with a given name wins and duplicates are reported. Global variable lists are read only from `configuration/globalVars` and `resource/globalVars`, never from inside a POU interface. Discovery and parsing are separate functions, so a variable is parsed the same way wherever it sits.
- **Why:** CODESYS leaves the standard location empty when the Device is exported (see `docs/xml-structure.md`), and a `globalVars` section is also a legal POU interface section.
- **Alternatives:** Only the CODESYS location (breaks on other tools' exports); a whole-tree search for `globalVars` (would turn POU-level sections into GVLs).
- **M2.1 amendment:** Decision 010 replaces project-wide name deduplication with deduplication of identical definitions within the same owner; conflicting definitions are retained.

## 010 — The parse model preserves comparison data (M2.1)
- **Decision:** The parse model must be lossless for everything M3/M4 may compare. A warning is not a substitute for keeping the data. Readable fields and structured nodes coexist with canonical XML for type declarations, initial values, return types and graphical bodies. Unknown type/value shapes and generic FBD/CFC details remain available without reparsing the source file.
- **Why:** M2 discarded ladder semantics, ownership, task target types, qualifiers and complex declaration details. Distinct source programs could therefore produce equal models, making correct cross-reference and version comparison impossible.
- **Ownership:** `Pou`, `GlobalVarList`, `Task` and `Variable` retain the enclosing configuration and application (the resource name). `None` means project/configuration scope, not an inferred application. Variable identity is `(configuration, application, scope, name)`. Deduplication compares POU definitions only within `(configuration, application, name)`. Identical copies collapse with a warning; conflicting definitions remain with a warning. Project POUs are independent of resource-local POUs.
- **Tasks and graphical bodies:** A task stores `PouInstance(instance_name, type_name)`; empty `typeName` falls back to the instance name. LD instructions retain kind, local ID, variable, negation, storage, edge and incoming connection IDs. Canonical instruction/body XML preserves other graph semantics, including generic FBD/CFC and vendor content. Local IDs are strings, preserving the XML identifiers without numeric coercion.
- **Declarations:** Recursive arrays and sized STRING/WSTRING types have readable names; `derived_types` exposes derived bases even inside arrays. The readable fields (`Variable.type`, `Variable.initial_value`, `Pou.return_type`) never contain XML: array and struct initial values show `(array)` / `(struct)`, types without a short form show `(struct)` / `(unknown)`, and an unknown leaf type tag shows its own name with a warning. Canonical `type_xml` / `initial_value_xml` / `return_type_xml` carry the full detail and distinguish declarations whose readable forms coincide. The model contains strings and dataclasses, never live XML elements.
- **Qualifiers:** Each variable stores `retain`, `nonretain`, `persistent` and `constant`, defaulting to false. For CODESYS mixed global lists, the top-level variables supply declarations and `MixedAttrsVarList` supplies the complete qualifier set by variable name. Nested lists never become extra GVLs. Sample 04 is the real-format reference.
- **Normalization (M2.3):** Canonical fragments use C14N 2.0 after assigning `n0`, `n1`, ... to the fragment's sorted namespace URIs. The empty namespace remains unprefixed and the reserved XML namespace keeps `xml`. Prefix numbering is independent of source prefixes, attribute order and the process-wide `ElementTree.register_namespace` state. C14N sorts attributes and uses canonical XML escaping and explicit end tags. Indentation is removed only from pure element content: the parent has element children and neither its text nor any child tail contains non-whitespace text. Here whitespace means XML whitespace (space, tab, CR and LF). An effective `xml:space="preserve"` keeps that indentation too; it is inherited within the fragment until `xml:space="default"` resets it. A child's tail follows its parent's setting. All other parsed text is preserved verbatim, including leading/trailing/internal whitespace, mixed content and whitespace-only leaves. This preserves text content, not source spellings such as CDATA or entity references; XML parsing already normalizes source line endings. The fragment root's tail belongs to its surrounding document and is excluded.
- **Documented exclusions:** GUIDs, timestamps, device/library metadata, XML comments, graphical positions, LD network comments and CODESYS network titles remain excluded. Unknown vendor elements are preserved, even when their local names resemble layout tags; excluding an element does not discard its tail text. ST text retains whitespace apart from normalized line endings. M4 must choose semantic fields rather than compare project headers or diagnostics.
- **Alternatives:** Warning-only fallback (loses evidence); retaining only the original file (forces every consumer to parse XML); storing live ElementTree objects (poor JSON boundary and mutable shared state); deduplicating all equal names (merges different applications).
- **Revised in M2.2:** the first version let canonical XML depend on registered prefixes and put XML into the readable fields, which broke the `plcdoc parse` table. Fixed as described above; `is_derived` was dropped in favour of `derived_types`; `Task.settings` (CODESYS TaskSettings) and `Pou.comment` are kept. Still deferred to M3: `ProjectStructure`, `types/dataTypes`, POU methods/actions in `pou/addData`, and unifying the two ownership walks.
- **Revised in M2.3:** canonicalization preserves significant text and numbers prefixes by sorted URI, fixing M2.2's text stripping and attribute-order dependence. The CLI table is plain terminal output: only pipes are escaped and newlines replaced with spaces. This supersedes decision 008's proposed reuse for rendered Markdown; export escaping and rendered-text tests belong to M3.

## 011 — Cross-reference: data model and scope resolution (M3a)
- **Decision:** `plcdoc.xref.cross_reference(project)` is a pure function over the parse model (like `tables.py`), not a field of `Project`. It scans every code unit (POU body, action, method, property accessor) and returns a `CrossReference` with one `Reference` per identifier occurrence that resolves to a declaration, plus `unresolved` occurrences and `warnings`. Identifiers are resolved against declared scope; raw string matching is never used. The ST scanner is a tokenizer with a nesting-depth counter, not a full parser.
- **Scope paths:** one naming convention is shared by `Variable.scope`, `Location.unit` and `Target.scope`: `PLC_PRG`, `GVL_IO`, `FB_Drive`, `FB_Drive.M_Start` (method), `FB_Drive.A_Reset` (action), `FB_Drive.P_Speed.Get` / `.Set` (accessors), `ST_Drive` (DUT).
- **Records:** `Location(configuration, application, unit, line, column, local_id)` — ST uses 1-based line/column in the LF-normalised body text, LD uses the element's `local_id`. `Target(kind, configuration, application, scope, name)` with kind `variable`, `field` (struct member), `result`, `pou`, `method`, `property` or `action`; a variable target equals `Variable.identity` plus kind. `Reference(target, member, member_target, access, location, text, via)`: `target` is the head declaration, `member` the dotted member path after it (index contents and `^` excluded), `member_target` the declaration of the last member step when the types are known, `access` one of `read`, `write`, `readwrite`, `call`, `text` the path as written, `via` the `VAR_EXTERNAL` declaration when the head was an alias. `by_target(xref)` indexes each reference under its `target` and, when present, its `member_target`, at most once per key, in scan order.
- **Result symbols:** a function's own name, a method's own name and a property's name inside its accessors are `Target(kind="result")` with the unit as scope; the getter's `P_Speed` (written) and the setter's `P_Speed` (read) have distinct scopes `…P_Speed.Get` / `…P_Speed.Set`. Programs, function blocks and actions have no result symbol.
- **Owner chain:** lookups by name search objects owned by the unit's `(configuration, application)`, then `(configuration, None)`, then `(None, None)`, stopping at the first level with a match. Several retained definitions with the same name at one level (M2 keeps conflicting duplicates; a global may sit in two GVLs) → the first in parse order wins and a warning names the candidates. No name-to-object map is merged across owners.
- **Head lookup order:** unit variables → unit result symbol → owning POU variables (all sections) → owning POU methods/properties/actions → `THIS^` = the owning FB (`SUPER^` unresolved) → globals through the owner chain → POU, GVL, DUT names → enum value names (an enum literal, qualified or not, is skipped: not a reference, not unresolved) → `Unresolved(reason="undeclared")`. Continuation: a GVL or POU head resolves the next segment to that list's/POU's variable (so `GVL_IO.x` and `x` share a target); a DUT head is an enum literal or unresolved; a variable head makes the rest the member path.
- **Alias normalisation:** wherever a `Variable` declaration becomes a target (head lookup, GVL/POU-name continuation, member walk), a `VAR_EXTERNAL` declaration is replaced by the visible global of the same name, with the external declaration recorded in `via` when it was the head. No visible global → `Unresolved(reason="external without global")`.
- **Member walk:** `member_target` comes from a structural walk of the declaration's `type_xml`, never from `derived_types` (which flattens every nested `derived`): `derived` → the named POU/DUT through the declaring variable's owner chain; `array` → its base type; inline `struct` → its own fields; `pointer` or unknown → stop (`member_target=None`). Bit access (`w.3`) ends the path.
- **Access (ST):** the path immediately preceding `:=`, `S=`, `R=` or `REF=` at nesting depth 0 is written (this covers every control-flow boundary and `FOR` without statement-start detection; `REF=` reads its right-hand path); a path followed by `(` is a call; everything else is read, including `ADR(x)`, `SIZEOF(x)`, `x^` and index contents. Parameter direction rule: `input` → formal written, actual read; `output` (`=>`) → formal read, actual written; `inout` → both readwrite; `inout` + `constant` → both read; unresolved formal → `:=` input, `=>` output. A formal reference exists only where a formal name is written (`IDENT :=` / `IDENT =>`); positional actuals use the callee signature (formals in declaration order over `input`, `inout`, `output`) only to classify the actual, and an unknown signature means read.
- **Tokenizer:** skips `//`, `(* *)` (not nested), `/* */`, strings with `$` escapes and `{…}` pragmas; keywords are never identifiers; `IDENT#…` and `%…` are literals; names compare case-insensitively (`text` keeps the written spelling).
- **LD:** contacts read and coils write their `variable` text (negation, edge and storage do not change access); a block is a call on its instance variable and yields exactly one reference per pin, access by the direction rule merged over all its connections (fan-out never multiplies references); `inVariable` reads, `outVariable` writes, `inOutVariable` readwrites its expression; block-to-block wiring adds no references. Contact/coil/pin texts go through the same resolver as ST.
- **Why:** M3b needs a per-variable table of reads and writes with locations that survive M4's comparison. One record per occurrence, carrying both the head variable and the resolved member declaration, gives both views ("what does `PLC_PRG` do with `fbDrive`" and "where is `FB_Drive.xRunning` read") without keeping pairs consistent. A tokenizer with a depth counter is enough because the ST subset that matters for references is regular: paths, assignment operators, calls, members.
- **Alternatives:** full ST grammar (weeks, no gain for reads/writes); raw string search (matches `xOk` in both scopes, enum literals and comments); references stored in `Project` at parse time (couples the scanner to the parser, duplicates JSON); two references per member access; resolving `VAR_EXTERNAL` to the POU's own declaration (hides global writes); `derived_types` for member resolution (cannot tell a pointer to a DUT from an instance).
- **Open for M4 (ObjectId stability):** M3a reads ObjectIds only to classify `StructureNode.kind` and stores none (Decision 010 unchanged). Checked 2026-09-17: every object present in both files of the pairs 01→02 and 03→04 keeps its ObjectId; neither pair renames a POU, GVL or task, so stability across a rename is unverified. If a future sample confirms it, M4 may add `object_id` to `Pou`, `GlobalVarList`, `Task`, `DataType`, `Method`, `Property`, `Action` and `StructureNode` for rename detection, with an amendment to Decision 010 and a consistent-relabel noise test.

## 012 — M3a model extensions: DUTs, POU members, ProjectStructure
- **Decision:** `DataType(name, kind, base_type, base_type_xml, members, values, attributes, comment, configuration, application, vendor_xml)` with kind `struct`, `enum` or `other`; struct fields are `Variable`s with `scope` = the DUT name and `section="struct"`, and are not yielded by `all_variables()`. The enum base type is `None` unless the export carries `enum/baseType` (CODESYS does not export it); nothing is invented. `{attribute}` pragmas become `Attribute(name, value)` in declaration order (parsed on DUTs only, the sole element with a real example). `Pou` gains `methods: list[Method]`, `actions: list[Action]`, `properties: list[Property]`; `Method` and `Accessor` (`kind` `Get`/`Set`) carry their own variables, whose `scope` is the scope path (`FB_Drive.M_Start`, `FB_Drive.P_Speed.Get`), plus the same four body fields as `Pou`; `Property(name, type, type_xml, getter, setter, …)` uses named accessor fields so the XML order (Set before Get) is irrelevant. `Project.data_types` and `Project.structure` (a tree of `StructureNode(name, kind, children)`) are added. `StructureNode.kind` comes from joining the node's ObjectId with the ObjectIds read during parsing (configuration, application, gvl, pou, datatype, task, libraries, method, action, property); an unmatched id gives `kind=None` without a warning (folders are normal). ObjectIds are used transiently and never stored.
- **API changes to M2:** `Project.all_variables()` also yields method and accessor variables after their POU's own variables (methods in parse order, then each property's Get variables before its Set variables, fixed by the model regardless of XML order). `io_variables()`, `io_table()`, `variable_table()` and the CLI counts therefore include them; an addressed method variable appears in the I/O table with its scope path. `Variable.section` gains the value `"struct"`, which never comes from a `*Vars` tag. Everything else is additive (new classes, defaulted fields, new module).
- **Lossless fallback:** on `Pou`, `Method`, `Accessor`, `Property`, `Action` and `DataType`, every direct `addData/data` the parser does not model is kept as canonical XML in that element's `vendor_xml`; `interface/addData` is kept separately in `interface_vendor_xml` (on `Pou`, `Method`, `Accessor`, `Property`), so moving an extension between locations changes the model; unexpected child elements inside these wrappers (for example transitions) go to the wrapper's `vendor_xml` and are never parsed. Inside a preserved fragment, `objectid` data is stripped recursively; all other vendor content is kept. `GlobalVarList` and `Task` keep M2's behaviour (unknown `addData` dropped): a known gap deferred to M3b. `AccessModifiers` content, inheritance markers and interfaces are preserved this way, not modelled.
- **Parser:** one recursive ownership walk replaces `_iter_owned_elements` and `_iter_holders`; POUs, DUTs, GVLs and tasks all take their `(configuration, application)` from it. DUTs deduplicate like POUs (identical definitions within one owner collapse with a warning, conflicts are retained).
- **M3a review correction (B8):** recognized content without a field on its owning model is also residual XML. Accessor-level documentation stays in `Accessor.vendor_xml`; accessor interface documentation and returnType stay in `Accessor.interface_vendor_xml`. Variable sections declared on Property itself stay whole in `Property.interface_vendor_xml`, including qualifiers, initial values and vendor extensions; they do not enter `all_variables()`. Residuals keep source order and strip nested objectid data as above. This uses existing fields rather than adding model fields or inferring semantics from shapes absent in the real exports; it preserves comparison data and its location without changing the public model shape. Warnings describe preservation, not discarded data.
- **Why:** reuse of `_parse_variables`/`_parse_body` for every declaration site; one scope-path convention shared with Decision 011; a GUID-free model keeps Decision 010's exclusion and M4's semantic comparison; a location-preserving fallback keeps M4 from comparing two different files as equal.
- **Alternatives:** reuse `Pou` for methods (wrong `pou_type`, dedup key collisions); a generic `PouMember(kind, …)` (loses the property's Get/Set structure); storing `object_id` (enables rename detection but reopens Decision 010; can be added additively later); one flat `vendor_xml` per element (loses where an extension sat).
